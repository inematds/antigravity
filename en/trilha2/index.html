🎯 Your First App: From Problem to Localhost

Before writing a line of code: clearly define the problem, use AI as a sparring partner, generate an SOP, provide visual references, orchestrate parallel agents, plan, preserve context, and connect a database via MCP.

What it is:

The “55-5” rule: out of 60 minutes, spend about 55 understanding the problem and only about 5 rushing toward a solution. Most tutorials jump straight to the code — don’t do that.

Why learn:

A poorly defined problem leads to an app no one uses. Clarity at the start saves hours of rework.

Key concepts:

Problem definition · 55-5 rule · avoid rushing into code.

What it is:

Use AI as a training partner: ask it to challenge your reasoning and help define the problem. Then ask for a short SOP (procedure), no more than 800 characters.

Why learn:

The AI’s counterpoint exposes gaps early; the SOP becomes the roadmap that guides the build.

Key concepts:

Sparring · challenge the reasoning · SOP ≤ 800 characters.

What it is:

Give the agent visual references (screenshots of sites you like). AI is great at design, but it works much better with specifics.

Why learn:

"Make it look good" is vague; a reference screenshot conveys visual intent in seconds.

Key concepts:

Visual references · specificity · galleries (Awwwards, Dribbble, Mobbin, Land-book).

What it is:

In Agent Manager, you manage multiple agents and projects at the same time. Each workspace = one project, and you move much faster.

Why learn:

Parallelizing multiplies your output: while one agent works, you review or start another.

Key concepts:

Agent Manager · project-based workspace · parallelism.

What it is:

Treat each agent like an employee: give them SEPARATE tasks. Never assign two agents to the same task — they’ll collide and get in each other’s way.

Why learn:

It's like a team where no one does someone else's work: less conflict, more progress.

Key concepts:

Division of labor · avoid collisions · one agent, one task.

What it is:

Put the agent in planning mode: it proposes a plan, and you review and approve it as you would with an employee. Actions wait for approval in the inbox.

Why learn:

Approving the plan before execution keeps the agent from building the wrong thing.

Key concepts:

Planning mode · review · approval in the inbox.

What it is:

A .md file (e.g., Gemini.md) with the project rules — source, colors, purpose — that the agent rereads every time. It survives a context window “overflow.” A research.md file stores reusable research.

Why learn:

It's the project's long-term memory: the agent doesn't "forget" your decisions.

Key concepts:

Context file · context window · research.md.

What it is:

MCP (Model Context Protocol) is the "universal language" that lets apps and services communicate. Connect a database (Supabase) via token, and the agent creates the project and writes the SQL on its own.

Why learn:

With a connected database, your app stores real data — without you writing SQL by hand.

Key concepts:

MCP · token · Supabase · SQL generated by the agent.

🚀 Publish and maintain your app

Get the app off localhost: connect GitHub, deploy to Vercel, protect keys with env vars, enable analytics, debug with screenshots, commit often, roll back, and control API spending.

What it is:

Connect AntiGravity to GitHub via MCP to manage and publish repositories directly from the editor. Requires a Personal Access Token (fine-grained, with an expiration date) and Docker installed for the integration to work.

Why learn:

Publishing without leaving the editor reduces friction and keeps everything in one workflow.

Key concepts:

GitHub MCP · Personal Access Token · Docker.

What it is:

Vercel is the “bridge” from GitHub to the world: production hosting. Add New → Project → import the repo → publish, and the app goes live.

Why learn:

It's the step that turns a local project into something anyone can access through a link.

Key concepts:

Hosting · import repo · production.

What it is:

To protect API keys, the agent only names the variable; you paste the key into Vercel (Settings → Environment Variables) and redeploy. The key never appears in the code.

Why learn:

An exposed key in your code is the #1 security mistake — and it can be costly.

Key concepts:

Env var · naming vs. value · Redeploy.

What it is:

Enable Analytics and Speed Insights in the Vercel dashboard and install the package from the terminal (npm). You can then track traffic and performance, with a generous free plan.

Why learn:

Without data, you guess. With data, you improve what matters.

Key concepts:

Analytics · Speed Insights · npm · free plan.

What it is:

When the build fails, take a screenshot of the error logs and send it to the agent: "There was a deployment error; fix it." Use DevTools (Console/Network) and send a screenshot of the error.

Why learn:

The image gives the agent the exact context — it fixes things much faster.

Key concepts:

Error logs · screenshot · DevTools (Console/Network).

What it is:

Commit often. Real story: coding for 6 hours without committing and losing the best version. Version control is your safety net.

Why learn:

Each commit is a safe return point — you never lose more than your most recent piece of work.

Key concepts:

Frequent commits · history · a recovery point.

What it is:

In Vercel: Deployments → choose the previous stable version → Redeploy. It's "going back in time." You can also revert through GitHub.

Why learn:

A bad deployment is no longer cause for panic: you can restore the good version in seconds.

Key concepts:

Deployments · stable version · Redeploy · revert in GitHub.

What it is:

Set an API spending budget so you don’t get hit with a huge bill. Make the repository private after publishing.

Why learn:

A spending limit prevents bill surprises; a private repo protects your code and keys.

Key concepts:

API budget · spending cap · private repository.
